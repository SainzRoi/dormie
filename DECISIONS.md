# Implementation decisions

1. **Architecture:** FastAPI with a Jinja-served HTML shell and plain JavaScript fetching REST endpoints. This avoids a frontend framework/build while providing the seven requested page equivalents. Business services are independent of FastAPI and raise `DomainError`.
2. **Seven domain entities:** No manager, room, class schedule, temporary absence, or workload-history table. Alembic's version table is infrastructure. Additions are resident username/password hash/active status/join time, chore active status, and assignment rationale. The rationale stores allocation-time evidence so later availability/ratings/history changes cannot rewrite the explanation.
3. **Authentication:** Argon2id, signed HttpOnly session cookie, eight-hour expiry, SameSite=Strict, per-session CSRF for all mutations, token rotation at login/register. No email, password-reset, persistent login-attempt table, or account administration. Set a persistent environment secret; a random fallback is development-only. This is a local demo, without public-hosting rate limiting or centralized session revocation.
4. **Shared catalog:** Every authenticated resident can create/edit/retire chores, as allowed in the brief. Chores with history cannot change weekday; this prevents contradictions with historical due dates. Names/descriptions can change and are not snapshotted. No destructive delete API.
5. **Availability:** Seven boolean rows per resident after the first save; missing rows mean unavailable. Weekday availability is not a promise that no unexpected commitments exist. A resident must have joined by an assignment's due date to qualify.
6. **Week and history semantics:** Monday–Sunday in Asia/Manila. Historical burden averages the previous four calendar weeks that have ended before both target and current local week; it includes responsibility for unfinished work. Calendar weeks without assignments count as zero, and weeks ending before joining are excluded. This avoids granting residents an artificially high historical average when no work was scheduled.
7. **Metrics:** Selected-week totals are separate from all-time cumulative totals. Cumulative includes future planned weeks. All-time average includes every calendar week from the later of joining week and first recorded week through the later of selected/latest-recorded week. Zero-point residents and inactive historical residents remain visible. Charts cover selected week plus three preceding weeks; the fairness four-week sum instead uses four ended weeks. The SQL view and independently tested query use the same responsibility attribution.
8. **Allocation:** A deterministic greedy heuristic, not a proof of global optimality. Exact floating-point means are retained (no deliberate rounding internally); two decimals are displayed. Existing assignments, points, and rationale never change on generation retry. Unrated active chores block generation even if other chores already have assignments. No-availability chores produce warnings and can be filled later. Past-week generation is only available to the local seed service, not through the API.
9. **Delegation lifecycle:** Original assignee requests, designated recipient accepts/rejects, original assignee cancels pending requests. Availability and active status are rechecked on acceptance. Accepted requests are final, without chains. Later availability changes do not revoke responsibility. Completing a task automatically cancels pending requests. Request timestamp and rejected/cancelled rows are preserved; no extra response timestamp was added.
10. **Transactions:** SQLite `BEGIN IMMEDIATE` starts before authentication/read-modify-write for mutations; this serializes writes and avoids race-prone allocation and delegation decisions. Foreign keys and unique/check/partial-index constraints add protection. API dependencies roll back failed operations. SQLite is the supported/test-target backend; ORM types and reporting SQL are largely portable, but PostgreSQL concurrency locks, weekday checks, and equivalent due-date triggers must be implemented/tested before claiming PostgreSQL support.
11. **Cross-table integrity:** SQLite migration triggers validate assignment due date on insertion/update and prevent changing a chore's weekday with history. Monday/Sunday checks and unique Mondays prevent overlapping valid weeks. Direct database edits to existing weeks are unsupported; no week-update route exists.
12. **Demo continuity:** Seed fixture dates, ratings, availability, and allocation reference date are fixed. Existing records are not reset on repeat runs. The optional accepted-delegation demo is separate and idempotent. Demo passwords are intentionally documented; use only for classroom/local data.
13. **Scale and scope:** Reporting uses simple ORM queries with zero filling plus a SQL view. This is appropriate for one small dorm, not large multi-tenant datasets. No scheduler, notifications, duration scoring, verification of cleaning quality, or optimization solver.
14. **Environment limitation:** The host default Python is 3.10, but a cached Python 3.12 runtime supported real database/service tests. Network restrictions prevented installing FastAPI, Alembic, pytest, and Uvicorn. Those integration and launch checks remain unverified; this is documented instead of claiming the full definition of done has passed.
